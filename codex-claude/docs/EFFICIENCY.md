# Use the factory efficiently

This guide describes requirements for the factory generated by [GENERATION.md](../GENERATION.md). Its commands are available after generation, not merely after cloning this prompt package. The ten roles, documentation stage, five independent reviews and exact human merge approval remain required.

## Install once and reuse

For a new app, select a trusted compatible versioned factory starter if available. Verify its manifest and offline results, then preview installation conflicts. A checksum proves integrity, not publisher trust. Never import another machine's jobs, owner/session IDs, permissions, context, credentials or usage.

If there is no verified starter, generate the factory once. The generated helper must provide sanitized export, verification and installation for future projects. This prompt repository does not yet ship a complete prebuilt runtime. An existing app needs a focused upgrade rather than another full generation.

## Give one clear feature brief

In the owning Codex chat, provide a compact request:

~~~text
$factory Add SAVE10 discounts to checkout.

Expected behavior:
- A valid SAVE10 code reduces the eligible subtotal by 10%.
- Invalid or expired codes explain the problem without losing the cart.
- Document the new merchant and customer workflows.

Constraints:
- Reuse the existing pricing and authentication logic.
- No new dependency, deployment or production-data changes.

Verification:
- Test valid, invalid, expired and rounding cases.
- Keep the existing acceptance checks passing.
~~~

Point to relevant existing files or examples when known. Let the owner inspect the implementation rather than paste whole repositories, logs or old chats. Combine related feedback into one clear message. A new requirement after the contract is frozen needs an explicit scope update and affected revalidation.

## Keep context focused

The generation prompt is for setup and audit. Workers get concise common rules, their own role, the current objective, exact commit/spec/contract IDs and relevant file paths. They can read more in-scope evidence when needed. They must not receive the full generation prompt on every turn.

The owner maintains one compact project map and refreshes changed sections. Freshness includes repository/config/instruction/source fingerprints; ignored local tools and effective permissions need their own checks. Each worker reads its task packet rather than repeating whole-project exploration. Independent reviewers still inspect authoritative code and contract, without copying another reviewer's verdict.

Resume the recorded builder for source revisions. Supply the changed-context and all five report paths. After implementation, the documentation writer assesses existing baseline coverage once, then updates affected pages on later features. Preserve session continuity and role-specific context.

## Bound routine output

The proposed default inline tool output is at most 50 lines and 16 KiB, with full output saved privately. Include exit status, useful failing assertions/stack frames, explicit truncation and the log path. A worker may inspect the relevant omitted section. A short summary is not substitute acceptance evidence.

Reports should contain the required verdict and commit, concrete findings, evidence and limitations. Keep repeated background out. Never cut off a serious finding or hide an error to meet a size target. Application documentation should be complete for its audience, while avoiding unrelated boilerplate.

## Reuse valid work

Local prerequisite checks do not call models. Deduplicate live access checks for the same model and verified environment. The proposed readiness TTL is 60 minutes; version/path, project, permission/auth/network changes or a new failure invalidate it earlier. Unknown fingerprints require rechecking, not blind reuse. Shared model access does not prove each role's assigned file access or completed work.

Run focused checks while coding. Run the frozen required suite on the final code-and-documentation commit. Reuse matching artifacts only when the contract permits it; preserve QA's independent verification. Source/docs/spec/target/environment changes invalidate affected results. Do not rerun successful unchanged checks without a concrete reason.

## Avoid retry loops

The default controller diagnostic retry allowance is zero: one initial attempt, then diagnose the result. Observable provider retries are recorded separately. Any enabled automatic retry needs a known safe, conclusively failed diagnostic and valid authorization, with a bounded policy.

A timeout is not proof the process stopped. Reconcile the original session/process before resume. Never start a second builder, replace its UUID or clear a lock to escape an uncertain run. Group the five review findings into one rework pass after all five reports arrive.

## Configure budgets deliberately

The generated factory/efficiency.json must validate policy types/ranges and reject unknown fields. Token and API-equivalent USD limits default to null; no arbitrary budget is invented. Set job/stage limits deliberately for your task, with an alert at 80% of a configured limit unless changed in policy.

Before new paid dispatch, compare recorded usage, in-flight estimates and available completeness against the policy. Missing evidence must not become zero. A configured enforcing budget that cannot be evaluated blocks new calls and explains why. On exhaustion retain partial artifacts, sessions and spend history. Raising a limit needs actual human authorization; it is separate from merge approval.

These controls stop new dispatches. They do not guarantee that an already running provider request or delayed telemetry cannot exceed a predicted amount. Claim a hard provider cap only when an actual enforced runtime/provider mechanism has been verified. Estimated API-equivalent cost is not necessarily an additional subscription bill.

## Inspect real measurements

After generation, from the factory workspace:

~~~powershell
node factory/scripts/factory.mjs efficiency
~~~

Expected: a local summary of validated policy and existing measured usage by role/stage, retries, durations, cache categories and budget/freshness warnings. It must not start a model, a new owner or another repository scan. The dashboard Usage view shows the same sanitized information through the single home link.

Compare similar completed tasks using the recorded token categories, elapsed time, retry count and quality/review outcomes. Mark missing data partial/unavailable. Input bytes can be reported as bytes, not guessed token counts. Session reuse does not guarantee a cache hit; only actual exposed cache telemetry supports that claim.

## What this update changes

The reusable generation instructions are shorter and require focused task packets, bounded inline output, safe readiness reuse, retry accounting, validated budgets and local efficiency diagnostics. Savings for future generated factories must be measured from their real execution. Documentation checks in this prompt repository do not prove live token savings or a finished prebuilt starter.

For failures, use [TROUBLESHOOTING.md](TROUBLESHOOTING.md). For first-time setup, use [SETUP.md](SETUP.md).
